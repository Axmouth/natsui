SETUP GUIDE

A dashboard.
With its history intact.

Run Natsui alongside NATS, protect dashboard access, and keep observations when the container changes. SQLite needs a volume, not a database service.

START EXPLORING

A real cluster in one command

Docker Desktop with Linux containers, or Docker Engine with Compose 2.34+, starts three NATS servers, the dashboard and scripted traffic.

PowerShell / Bash / Zsh
docker compose -f oci://ghcr.io/axmouth/natsui-demo:latest up -d --wait

Open 127.0.0.1:4321. This is an unauthenticated local tryout with reviewed broker edits enabled. Only the dashboard port is published, on loopback. The browser demo needs no installation and contains entirely synthetic data.

Stop with the same command reference followed by down instead of up -d --wait. Named volumes remain. Adding -v deletes this demo's history and broker data.

CONNECT AN EXISTING BROKER

Dashboard access-key login

This setup gives one operator identity an expiring login session. NATS credentials remain separate. All holders of the dashboard key share its configured capabilities; individual accounts and roles are not implemented.

1. Generate the dashboard key

A separate named volume holds the key. Generation refuses to overwrite an existing file.

Generate once
docker run --rm -v natsui-auth:/data ghcr.io/axmouth/natsui:latest --init-auth /data/access.key

Display the generated key locally for sign-in. Store it in a password manager; this command's output is a secret.

docker run --rm --entrypoint cat -v natsui-auth:/data:ro ghcr.io/axmouth/natsui:latest /data/access.key

2. Start Natsui on the broker's network

Replace NATS_NETWORK and NATS_SERVICE with the existing private Docker network and NATS service name.

History and secrets use separate volumes
docker run -d --name natsui --network NATS_NETWORK -p 127.0.0.1:4321:4321 -e NATSUI_URL=nats://NATS_SERVICE:4222 -e NATSUI_PROFILE=production-observer -e NATSUI_AUTH_TOKEN_FILE=/run/natsui-auth/access.key -v natsui-data:/data -v natsui-auth:/run/natsui-auth:ro --read-only --cap-drop ALL --security-opt no-new-privileges:true ghcr.io/axmouth/natsui:latest

The network makes the broker reachable; it does not grant broker permissions. For authenticated NATS, mount a dedicated restricted credentials file read-only and set NATSUI_CREDS, or configure supported URL credentials. Private CA and mutual TLS options are covered in the NATS identity and TLS guide. NATSUI_MONITOR_URLS optionally enables native node and connection metrics.

3. Sign in

Open 127.0.0.1:4321 and enter the access key. Sessions expire after eight hours; Sign out revokes the current session. Restart invalidates every session. The key is loaded at startup, so rotation requires a restart. A missing or malformed configured key stops startup.

This remains a local HTTP deployment. Public HTTPS/proxy support and team authorization are separate work. Login does not grant NATS permissions or enable writes. The default is read-only; reviewed edits require both NATSUI_ALLOW_WRITES=1 and broker authorization.

Compose alternative and key rotation

Download the authenticated Compose file after initializing the auth volume above. It uses the same named volumes and defaults to a broker reachable through host.docker.internal:4222. Override NATSUI_URL as needed, then run:

docker compose -f compose.auth.yaml up -d --wait

A broker listening only on host loopback may not be reachable through the Docker gateway. The shared-network command above avoids that limitation.

For rotation, generate a new file such as /data/access-next.key in the auth volume. Recreate Natsui with the new NATSUI_AUTH_TOKEN_FILE path and the same history volume. The old process and its sessions must stop before the old key is revoked. Losing a key does not require deleting history.

WITHOUT DOCKER

The native binary works too

Download a matching native artifact or build the repository with cargo build --release --locked. No Node runtime or separate database is needed.

PowerShell startup
New-Item -ItemType Directory -Force local-secrets, data
.\natsui.exe --init-auth .\local-secrets\dashboard.key
$env:NATSUI_AUTH_TOKEN_FILE = "$PWD/local-secrets/dashboard.key"
$env:NATSUI_DATA_DIR = "$PWD/data"
$env:NATSUI_URL = 'nats://127.0.0.1:4222'
$env:NATSUI_PROFILE = 'production-observer'
.\natsui.exe
Bash / Zsh startup
mkdir -p local-secrets data
./natsui --init-auth ./local-secrets/dashboard.key
export NATSUI_AUTH_TOKEN_FILE="$PWD/local-secrets/dashboard.key"
export NATSUI_DATA_DIR="$PWD/data"
export NATSUI_URL=nats://127.0.0.1:4222
export NATSUI_PROFILE=production-observer
./natsui

Read the key file locally to sign in. Generate it once; subsequent starts reuse it. Restrict secret/data directory access with OS permissions. Native connection credentials use the same NATS environment variables as the container.

PERSISTENCE

Mount the whole SQLite directory

The image sets NATSUI_DATA_DIR=/data. The native default is ./data, relative to the working directory. Use a stable absolute native path, or a named Docker volume such as -v natsui-data:/data.

Do not mount only natsui.sqlite3.

SQLite may also need natsui.sqlite3-wal and natsui.sqlite3-shm. The complete directory must be writable and persistent.

Stored in the data volumeKept separately
Observation history, dashboard settings, activity, incidents and profile bindingsDashboard access key and NATS credentials in read-only secret mounts
SQLite database and its WAL/SHM companionsLogin sessions in process memory; restart signs everyone out
Resource names and operational metricsMessage payloads are fetched on demand and are not persisted by Natsui

Named volumes survive container replacement. The root Compose file uses a project-prefixed volume; changing its project name can select new, empty storage. The authenticated example explicitly names natsui-data. down -v removes its history volume but retains its external auth volume.

The image runs as UID/GID 10001. Fresh named volumes inherit the image's data-directory ownership. Bind mounts and restored directories must allow that user to write the directory and companion files. Use local storage and one dashboard process per data directory, not a shared NFS/SMB mount.

Default retention is seven days and the serialized history budget is 128 MiB. Physical SQLite/WAL files can be larger. A persistent volume is not a backup.

BACKUP AND RECOVERY

Stop. Copy the directory. Verify the restore.

For the named container and volume above, stop the only writer before archiving. Run from an existing local backup directory. The helper runs as root to preserve file ownership; the source mount is read-only.

docker stop natsui
docker run --rm --user 0 --entrypoint tar -v natsui-data:/data:ro --mount "type=bind,source=${PWD},target=/backup" ghcr.io/axmouth/natsui:latest -czf /backup/natsui-data.tar.gz -C /data .
docker start natsui

Check backup success before treating the archive as usable. Prefer timestamped filenames to retain prior backups. A live copy of the database alone can miss committed WAL transactions. Online backups require SQLite's backup API or equivalent tooling; Natsui has no backup button yet.

Restore into a fresh volume

docker volume create natsui-restored-data
docker run --rm --user 0 --entrypoint tar -v natsui-restored-data:/data --mount "type=bind,source=${PWD},target=/backup,readonly" ghcr.io/axmouth/natsui:latest -xzf /backup/natsui-data.tar.gz -C /data .

Start a replacement dashboard using -v natsui-restored-data:/data, a different container name/port for the drill, and the same profile and NATS identity. Use the original image version or a compatible upgrade. Check readiness, sign in, and inspect settings and history before replacing the original instance. Never restore over a running database.

The complete deployment guide covers rotation, filesystem permissions and lifecycle details. SQLite WAL and the backup API document the underlying storage requirements.
